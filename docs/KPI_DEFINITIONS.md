# KPI Definitions README

This document explains the KPI outputs generated by the dashboard reporting service.
It is written for business readers first: what each KPI means, why it matters, and what the output looks like.

## Scope and Assumptions

- Complaint statuses used in reporting: `open`, `in_progress`, `closed`, `cancelled`
- Priority levels used in reporting: `critical`, `high`, `medium`, `low`
- Main source: `DashboardService.get_dashboard_stats(...)`

## Reporting-Period Date Anchor (read this before changing any KPI's filter)

Every KPI is scoped to the selected year/month/quarter/plant, but **which date field decides "is this complaint in the selected period" depends on the KPI family** — this is deliberate, not an oversight, and the two families must not be merged:

- **Volume/trend KPIs** (totals, monthly/quarterly breakdowns, Pareto/customer/product breakdowns, the year picker itself, acknowledgement delay) are scoped on `period_date_column()` = `COALESCE(customer_complaint_date, complaint_opening_date)`. This matches standard complaint-scorecard/IATF reporting practice: a complaint counts in the period the **customer** raised it, not whenever the plant got around to opening the formal 8D. Anchoring on the opening date instead would let slow intake processing quietly shift a complaint into a later reporting period — exactly the kind of distortion an audit would flag. The fallback to `complaint_opening_date` only applies when the customer date is genuinely missing, so a complaint is never silently dropped from every chart over one missing field.
- **Process-execution/SLA KPIs** (`overdue_complaints`, `overdue_steps`, `overdue_vs_toclose_by_plant`, `cqt_lateness`, `resolution_cycle_time`, `step_sla_compliance`, `cs2_sla_compliance`, `complaint_ageing`, `no_due_date_count`) are scoped on `complaint_opening_date` directly. Their SLA clocks (`D_STEP_SLA_DAYS`, `due_date`) are anchored on the opening date at creation time (see `complaint_service._sla_anchor_for`), so their reporting period must match — asking "was this on time" only makes sense relative to when the internal clock actually started.

In code: `DashboardService.get_dashboard_stats` builds both `base_filter` (volume/trend) and `ops_filter` (process/SLA) from the same `_build_filter(...)`, differing only in the `date_column` argument. When adding a new KPI, decide which family it belongs to by asking: *does this KPI's core calculation involve `complaint_opening_date`, `due_date`, or a step SLA deadline?* If yes, use `ops_filter`. Otherwise use `base_filter`.

`/available-years`, `/stats/realtime`, and `/stats/comparison` (in `app/api/routes/dashboard.py`) use the same `period_date_column()` as the main dashboard's volume/trend KPIs, so the year picker and every "total complaints"-style number agree across all three endpoints.

## 1 Volume and Trend KPIs

### total_complaints

- Business definition: Total number of complaints in the selected period.
- Role: Headline workload and baseline for most other KPIs.
- Example:

```json
{
  "total_complaints": 184
}
```

### top_plant

- Business definition: Plant with the highest complaint volume in the selected period.
- Role: Quick hotspot indicator for leadership focus.
- Example:

```json
{
  "top_plant": {
    "plant": "MONTERREY",
    "count": 47
  }
}
```

### monthly_data

- Business definition: Monthly complaint count by plant and monthly total.
- Role: Trend monitoring and seasonality detection.
- Example:

```json
{
  "month": "Mar",
  "MONTERREY": 8,
  "KUNSHAN": 3,
  "CHENNAI": 2,
  "total": 21
}
```

### total_by_plant

- Business definition: Total complaints by plant for the selected period.
- Role: Plant-to-plant comparison and ranking.
- Example:

```json
{
  "plant": "MONTERREY",
  "count": 47
}
```

### quarterly_by_plant

- Business definition: Complaint totals grouped by quarter and plant.
- Role: Executive-level performance view by quarter.
- Example:

```json
{
  "quarter": "Q1",
  "MONTERREY": 19,
  "KUNSHAN": 11,
  "total": 54
}
```

## 2) Target and Performance KPIs

### monthly_targets

- Business definition: Monthly target per plant (derived from previous-year baseline).
- Role: Benchmark for reduction strategy and target adherence.
- Example:

```json
{
  "monthly_targets": {
    "MONTERREY": 2.8,
    "KUNSHAN": 1.2
  }
}
```

### last_year_by_plant

- Business definition: Last-year total complaints by plant.
- Role: Baseline context for current-year interpretation.
- Example:

```json
{
  "plant": "MONTERREY",
  "count": 48
}
```

### monthly_vs_target

- Business definition: Actual complaints vs target, per plant and month.
- Role: Flags plants/months off target and improvement trajectory.
- Example:

```json
{
  "month": "Mar",
  "plant": "MONTERREY",
  "actual": 8,
  "target": 2.8,
  "delta": 5.2,
  "on_target": false
}
```

### monthly_vs_target_rolling_12_plus_3

- Business definition: Rolling 12 historical months + 3 future target months.
- Role: Reporting visual for trend continuity and near-term target outlook.
- Example:

```json
{
  "year": 2026,
  "month_num": 3,
  "month_label": "Mar-26",
  "plant": "MONTERREY",
  "actual": 8,
  "target": 2.8,
  "delta": 5.2,
  "is_future": false
}
```

## 3) Backlog and Status KPIs

### status_monthly

- Business definition: Monthly status distribution for all plants.
- Role: Portfolio health, closure balance, and backlog pressure.
- Example:

```json
{
  "month": "Mar",
  "open": 14,
  "in_progress": 9,
  "closed": 17,
  "cancelled": 1
}
```

### status_monthly_by_plant

- Business definition: Monthly status distribution by plant.
- Role: Local backlog control and closure discipline.
- Example:

```json
{
  "month": "Mar",
  "plant": "MONTERREY",
  "open": 6,
  "in_progress": 5,
  "closed": 7,
  "cancelled": 0
}
```

### open_closed_per_plant_monthly

- Business definition: Month-by-month open vs closed counts by plant.
- Role: Shows whether closure pace keeps up with intake.
- Example:

```json
{
  "month": "Mar",
  "plant": "MONTERREY",
  "open": 6,
  "closed": 7
}
```

### complaint_ageing

- Business definition: Age buckets for active complaints.
- Role: Identifies stale backlog and urgency risk.
- Example:

```json
{
  "buckets": [
    { "label": "0-7 days", "count": 11 },
    { "label": "8-30 days", "count": 9 },
    { "label": "31-60 days", "count": 4 },
    { "label": "61+ days", "count": 2 }
  ],
  "oldest_open": {
    "reference_number": "CMP-2026-AB12CD",
    "plant": "MONTERREY",
    "days_open": 73,
    "priority": "critical"
  }
}
```

### overdue_complaints

- Business definition: Complaints with passed due date and still not terminal.
- Role: Operational risk and escalation workload.
- Example:

```json
{
  "total": 7,
  "by_plant": [
    { "plant": "MONTERREY", "count": 4 },
    { "plant": "KUNSHAN", "count": 3 }
  ],
  "no_due_date": 0
}
```

### backlog_rolling_15

- Business definition: Rolling month-end backlog for 12 past + 3 future slots.
- Role: Long-view of backlog accumulation vs stabilization.
- Example:

```json
{
  "year": 2026,
  "month_num": 3,
  "month_label": "Mar-26",
  "plant": "MONTERREY",
  "actual": 22,
  "is_future": false
}
```

### in_progress_overdue_lag

- Business definition: In-progress complaints already past complaint-level due date.
- Role: Stuck-case tracker for management follow-up.
- Example:

```json
{
  "total_stuck": 5,
  "avg_days_overdue": 12.4,
  "flagged": [
    {
      "plant": "MONTERREY",
      "reference_number": "CMP-2026-AB12CD",
      "customer": "VALEO",
      "days_overdue": 19
    }
  ]
}
```

## 4) SLA and Process Execution KPIs

### acknowledgement_delay

- Business definition: Delay between customer complaint date and internal opening date.
- Role: First-response quality and customer responsiveness.
- Example:

```json
{
  "avg_days_overall": 1.6,
  "avg_days_cs1": 1.3,
  "avg_days_cs2": 2.2,
  "pct_within_1_day": 72.4,
  "pct_within_2_days": 89.1
}
```

### resolution_cycle_time

- Business definition: Time from complaint opening to closure.
- Role: End-to-end resolution speed KPI.
- Example:

```json
{
  "avg_days_overall": 18.3,
  "median_days": 14.0,
  "p90_days": 42.0,
  "by_plant": [{ "plant": "MONTERREY", "avg_days": 20.1, "count": 12 }]
}
```

### cs2_sla_compliance

- Business definition: SLA compliance specifically for CS2 complaints.
- Role: Critical complaint control and customer risk monitoring.
- Example:

```json
{
  "total_cs2": 32,
  "pct_acknowledged_on_time": 81.2,
  "pct_closed_on_time": 68.8,
  "open_past_sla": 6
}
```

### step_sla_compliance

- Business definition: On-time performance by 8D step (`D1`..`D8`).
- Role: Shows where process execution is late (not only complaint-level closure).
- Example:

```json
{
  "step": "D4",
  "sla_days": 5,
  "total": 28,
  "on_time": 21,
  "overdue": 7,
  "open": 3,
  "compliance_pct": 75.0
}
```

### overdue_steps

- Business definition: Overdue 8D steps by step code and plant.
- Role: Step-level bottleneck and operational load tracking.
- Example:

```json
{
  "step": "D4",
  "plant": "MONTERREY",
  "count": 5
}
```

### late_steps_by_plant

- Business definition: Total overdue steps by plant.
- Role: Plant process discipline comparison.
- Example:

```json
{
  "plant": "MONTERREY",
  "count": 14
}
```

### late_steps_rolling_12_plus_3

- Business definition: Rolling trend of late steps with future placeholders.
- Role: Visual trend for overdue-action improvement tracking.
- Example:

```json
{
  "year": 2026,
  "month_num": 3,
  "month_label": "Mar-26",
  "plant": "MONTERREY",
  "actual": 5,
  "target": 0.0,
  "delta": 5.0,
  "is_future": false
}
```

## 5) Recurrence, Risk and Escalation KPIs

### recurrence_rate

- Business definition: Share of repetitive complaints by month and plant.
- Role: Corrective-action effectiveness indicator.
- Example:

```json
{
  "month": "Mar",
  "plant": "MONTERREY",
  "total": 10,
  "repetitive": 3,
  "recurrence_pct": 30.0
}
```

### repetitive_distribution

- Business definition: Distribution of complaints by repetitive number bucket.
- Role: Recurrence intensity view.
- Example:

```json
{
  "repetition_number": "0 - First",
  "count": 112
}
```

### repetitive_by_plant

- Business definition: Repetition buckets split per plant.
- Role: Plant-level recurrence profile.
- Example:

```json
{
  "plant": "MONTERREY",
  "repetition_number": "2",
  "count": 6
}
```

### claim_criticality_detail

- Business definition: Detailed claims with computed criticality score.
- Role: Risk ranking for management prioritization.
- Example:

```json
{
  "plant": "MONTERREY",
  "customer": "VALEO",
  "claim": "CMP-2026-AB12CD",
  "type": "CS2",
  "recurring": "Yes",
  "criticality": 10,
  "status": "in_progress"
}
```

### escalation_rate

- Business definition: Share of complaints escalated to plant manager level.
- Role: Escalation pressure and severity signal.
- Example:

```json
{
  "total_escalated": 21,
  "total_complaints": 184,
  "escalation_rate_pct": 11.4,
  "by_plant": [
    {
      "plant": "MONTERREY",
      "total": 47,
      "escalated": 9,
      "escalation_pct": 19.1
    }
  ]
}
```

### cqt_lateness

- Business definition: Overdue-step impact by CQT owner and plant.
- Role: Accountability and support prioritization.
- Example:

```json
{
  "total_late": 18,
  "by_cqt": [
    {
      "cqt_email": "owner@company.com",
      "late_complaints": 6,
      "total_steps_overdue": 11
    }
  ],
  "by_plant": [{ "plant": "MONTERREY", "late_complaints": 8 }]
}
```

## 6) Root Cause and Exposure KPIs

### process_pareto

- Business definition: Top internal process drivers linked to complaints.
- Role: Focuses root-cause effort on highest-impact processes.
- Example:

```json
{
  "process": "Molding",
  "total": 27,
  "MONTERREY": 12,
  "KUNSHAN": 9
}
```

### application_pareto

- Business definition: Top customer application drivers linked to complaints.
- Role: Exposure understanding by use context.
- Example:

```json
{
  "application": "Starter Motor",
  "total": 21,
  "MONTERREY": 10,
  "CHENNAI": 5
}
```

### defect_types

- Business definition: Complaint count by defect category.
- Role: Technical concentration and Pareto of defect modes.
- Example:

```json
{
  "type": "Dimension Out of Spec",
  "count": 19
}
```

### product_types

- Business definition: Complaint count by product type.
- Role: Product portfolio risk concentration.
- Example:

```json
{
  "type": "BRUSH",
  "count": 23
}
```

## 7) Detail Tables for Action

### open_claims_follow_up_by_plant

- Business definition: Operational list of open/late claims with ownership and risk hints.
- Role: Daily follow-up and triage.
- Example:

```json
{
  "plant": "MONTERREY",
  "quality_engineer": "qe@company.com",
  "claim": "CMP-2026-AB12CD",
  "status": "in_progress",
  "priority": "critical",
  "late": "Yes",
  "criticality": 10
}
```

### customer_claim_detail_by_plant

- Business definition: Claim-level customer detail rows by plant.
- Role: Customer review and account-level follow-up.
- Example:

```json
{
  "plant": "MONTERREY",
  "customer": "VALEO",
  "claim": "CMP-2026-AB12CD",
  "status": "open"
}
```

### defect_detail_by_plant

- Business definition: Claim rows with product line, operation type, and defect.
- Role: Root-cause workshops and defect deep-dive.
- Example:

```json
{
  "plant": "MONTERREY",
  "claim": "CMP-2026-AB12CD",
  "product_line": "BRUSH",
  "operation_type": "Molding",
  "defect_type": "Dimension Out of Spec"
}
```

### quality_engineer_summary

- Business definition: Open workload and lateness profile by quality engineer.
- Role: Capacity balancing and accountability.
- Example:

```json
{
  "quality_engineer": "qe@company.com",
  "open_claims": 9,
  "late_claims": 4,
  "total_criticality": 38,
  "avg_criticality": 4.22
}
```

### quality_engineer_system

- Business definition: Plant-level engineer coverage and late/open load.
- Role: Process-pilot readiness and resource planning.
- Example:

```json
{
  "plant": "MONTERREY",
  "qe_count": 3,
  "open_claims": 17,
  "late_claims": 6,
  "trained_count": null,
  "app_available": null
}
```

## 8) Supporting/Meta Outputs

### report_stats

- Business definition: Report and step progression statistics.
- Role: Governance of reporting process completion.
- Example:

```json
{
  "total_reports": 184,
  "report_status": [
    { "status": "draft", "count": 41 },
    { "status": "in_progress", "count": 99 }
  ]
}
```

### cost_by_step_plant

- Business definition: Cost allocation by 8D step and plant.
- Role: Financial lens on quality workload and process burden.
- Example:

```json
{
  "plant": "MONTERREY",
  "D1": 1200,
  "D2": 800,
  "D3": 2400,
  "total": 9200
}
```

### no_due_date_count

- Business definition: Active complaints without due date.
- Role: Data-quality KPI that protects SLA reliability.
- Example:

```json
{
  "total": 0,
  "by_plant": []
}
```

## Notes for Consumers

- All date-period filters should be treated as report scope controls, not KPI definitions.
- `total_open` in reporting should mean only `open + in_progress`.
- KPI consumers should read dictionary keys exactly as returned by backend payload contracts.
